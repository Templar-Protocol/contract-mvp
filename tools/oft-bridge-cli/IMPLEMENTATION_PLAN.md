# Ralplan: Templar LayerZero OFT Bridge Operator CLI

## Review target
Build an explicitly OFT-only, testable Rust CLI in `/home/common/projects/templar/contracts` for instantiating and operating direct LayerZero Stellar/Soroban ↔ EVM OFT routes: wrap eligible non-USDC Stellar assets as Soroban `LockUnlock` OFTs paired with EVM mint/burn OFTs, configure and verify peers/options/security stacks, test both legs, recover permissionless delivery steps, and reconcile lockbox/supply/in-flight obligations.

This plan is deliberate because it handles signing credentials, contract ownership, custody accounting, and potentially production mutations.

## 1. Requirements and boundaries

### In scope
- New workspace CLI crate: `contracts/tools/oft-bridge-cli`, package `templar-oft-bridge-cli`, binary `tmplr-oft-bridge`.
- Route lifecycle: initialize state, preflight external artifacts/endpoints, build/deploy Stellar and EVM OFTs, configure peers/Type-3 options/ULN DVNs and executors, read back effective configuration, run capped forward/reverse leg tests, inspect LayerZero Scan, perform permissionless commit/receive recovery, and reconcile custody.
- Native Rust Soroban transaction simulation/signing/submission/status polling for asset transfers, canaries, views, and qualified recovery uses one canonical stack: `soroban-client = 0.5.5` and its `stellar-baselib = 0.5.6` transaction/XDR types, plus `stellar-strkey` only for address codecs. Do not expose or mix separate workspace `stellar-xdr` 25/26 types on transaction paths; official LayerZero config XDR is converted at a single byte-vector boundary after golden qualification; privileged LayerZero configuration writes use native pinned ABI/XDR after qualification against official source and golden vectors.
- Native EVM JSON-RPC, ABI calls, keystore signing, receipts, and logs using workspace Alloy 1.x.
- Reproducible, pinned official LayerZero source/artifact custody without modifying LayerZero mechanisms.
- Human and machine-readable output, versioned route state, and append-only message ledger.

### Out of scope
- USDC OFT routes: reject with a typed error directing operators to Circle CCTP.
- Custom debit/credit/escrow, relayer, DVN, executor, token, or messaging logic.
- Frontend integration, production rollout, asset issuer authorization, or canonical-asset policy changes.
- Moving secrets into repository files or state manifests.
- Automatic mainnet canaries.

### Invariants
1. Official LayerZero Stellar OFT and EVM OFT contracts remain unchanged; only a minimal constructor wrapper may bind name/symbol/endpoint/delegate.
2. Non-USDC topology is Stellar SEP-41/SAC `LockUnlock` → EVM mint/burn OFT. USDC is refused before artifact or signer access with `unsupported_use_cctp`; implementing or testing Circle CCTP is explicitly outside this OFT CLI and this plan, per the requirement that the OFT CLI direct USDC operators to CCTP.
3. Cross-VM shared decimals are exactly 6 because unchanged `@layerzerolabs/oft-evm@4.0.1` hardcodes `sharedDecimals() == 6`; Stellar token local decimals must be at least 6, and any other requested/effective shared decimals fail before deployment/adoption. Every mutation is simulate/readback-first; configuration success means effective state matches the requested route, not merely a successful receipt.
4. State is network/chain/EID-bound. A manifest cannot be reused across mismatched endpoints or chain IDs.
5. Secrets enter through keystore/identity paths or environment-backed providers; never argv, JSON output, logs, manifests, or error strings.
6. Canary sends are capped and use a canonical `LegIntentV1`. Mainnet mutation, signable proposals, and execution ingest are hard-disabled in v1 as `production_mutation_unsupported_v1`; mutable files can never authorize production.
7. Reconciliation uses raw common units and an append-only message ledger with stage-delta conservation. Each unique packet contributes exactly one mutually exclusive stage delta; duplicate or unknown records never contribute silently. The invariant is `expected_lockbox = normalized_evm_supply + pending_reverse_after_burn + lockbox_retained_fee_or_dust + pending_forward_locked_not_minted`, and `deficit = max(0, expected_lockbox - observed_lockbox)`, `surplus = max(0, observed_lockbox - expected_lockbox)`. This reproduces the captured `lockbox=2,000,000, supply=0, pending_reverse=2,000,000` state as zero deficit.
8. Message security configuration is snapshotted at send time. Later config writes never rewrite an existing packet; recovery records preserve the packet's original effective stack.
9. Existing dirty files in `contracts/` are user work and must not be reset, absorbed, or reformatted.

### Assumptions execution must verify
- `soroban-client 0.5.5`/`stellar-baselib 0.5.6` and workspace Rust 1.86 remain compatible with current Stellar protocol/Soroban RPC for constructor-bearing CreateContractV2, authorization entries, envelopes, meta, and events.

- Official LayerZero source revisions and EVM npm package versions are pinned in a committed lock file and reproducibly buildable in the operator environment.

## 3. RALPLAN-DR

### Principles
1. Native typed transactions and qualified pinned ABI/XDR encodings own every runtime mutation; subprocesses are restricted to official contract builds and a narrowly qualified Foundry-keystore signing fallback.
2. Read effective state, not intended config.
3. Append-only custody evidence; never hide or overwrite unresolved packets.
4. Official contracts and registries are dependencies, not code to fork.
5. Small CLI surface with composable commands; no daemon, database, plugin system, or generic multi-chain framework.

### Top decision drivers
1. Testability of encoding, signing, state transitions, and failure recovery without live-chain tests.
2. Credential safety and deterministic mutation gates.
3. Reproducibility across Stellar and EVM despite different toolchains/artifact ecosystems.

### Option A — Fully native Rust, including contract compilation and identity management
- Pros: one binary and typed interfaces end to end.
- Cons: duplicates `stellar contract build`, Solidity/npm/solc/Foundry artifact resolution, and identity-store behavior; materially increases dependency and custody surface.
- Decision: reject. Native runtime operations do not justify reimplementing upstream build tools.

### Option B — Shell orchestration around `stellar`, `forge`, `cast`, and TypeScript devtools
- Pros: shortest prototype and closest to the proven session commands.
- Cons: correctness depends on stdout parsing, quoting, CLI version drift, and secret redaction; hard to unit-test XDR/ABI/config invariants.
- Decision: reject as the primary architecture. Retain a narrow, injected subprocess adapter only for official builds and keystore fallback.

### Option C — Thin native Rust runtime with build-only upstream adapters
- Pros: typed codecs/RPC/signing/ledger; deterministic unit tests; reuses locked workspace dependencies; leaves artifact compilation to official tools.
- Cons: must maintain two RPC clients and explicit artifact manifests; Alloy keystore compatibility needs qualification.
- Decision: choose. Rust controls desired-state validation, signer selection, ABI/XDR encoding, simulation, signing, broadcast, journaling, independent readback, canaries, recovery qualification, and reconciliation. Pinned official tools own only reproducible contract compilation and a separately qualified keystore-signing fallback.

Every mainnet-classified chain command shown with `[--execute|--proposal-out FILE]` is rejected as `production_mutation_unsupported_v1`. RPC credentials are secret-provider inputs. URLs and headers come only from named environment variables or mode-0600 non-symlink files; never literal argv URLs. State persists only redacted provider labels and public origin `{scheme, host, port}` after stripping userinfo, path/query tokens, and headers. Error/log/JSON redaction removes URL userinfo, query values, authorization/API-key/cookie headers, and sentinel secrets. Provider files are read after environment classification needs them but before any mutation artifact; their contents never enter journal hashes.

Before global context resolves route state, RPC/provider files, artifacts/build tools, or signer/keystore inputs, a bounded pure parser/pre-dispatch `AssetRequestV1` classifier runs for every asset-introducing/binding command. For `asset wrap` it reads only typed asset flags; for `init --desired` and `adopt --desired` it opens only the explicitly named desired-route file with create-independent read-only/no-follow, size limit, and minimal asset-header decoding—before any route/RPC/artifact/signer path. It examines asset kind/identifier against a release-reviewed network-specific known-USDC identifier table. `usdc` or a known USDC identifier returns `unsupported_use_cctp` plus the appropriate Circle CCTP direction and exits. Only a classified non-USDC request proceeds to state/context loading. Sentinel tests for asset wrap, init, and adopt prove the USDC result wins even when state/provider/artifact/signer paths are inaccessible or secret-bearing. CCTP implementation/testing remains out of scope. `asset wrap` rejects known USDC identifiers and `--asset-kind usdc`; it records `unsupported_use_cctp` without mutation. Read-only mainnet inspection validates every `AssetPolicyV1` evidence digest and account-role exclusion; no mainnet signer or mutation path exists in v1.

## 5. Ordered implementation plan

Before Step 1, define these separate authorities:
- `DesiredRouteV1`: immutable canonical JSON (RFC 8785/JCS), content-addressed by SHA-256. It binds schema version, environment, asset identity and typed asset-policy claims, chain IDs/EIDs/endpoints and code hashes, artifact-lock digest, complete official OFT/library/DVN/executor/options/economic/rate-limit/admin state, concrete authority topology, caps, finality policy, and a unique route ID. Testnet desired routes may be locally authored.
- `LocalPreparationV1`: a closed enum for `BindRoute`, `BuildArtifact`, `AdoptRoute`, and `ImportEvidence`. These produce integrity-bound local custody artifacts but are not on-chain authority and carry no synthetic sequence/nonce.
- `OperationV1`: a closed, code-owned exhaustive transaction enum: deployment (`InstallStellarWasm`, `DeployStellarOft`, `DeployEvmOft`); authority (`BeginStellarOwnershipTransfer`, `AcceptStellarOwnership`, `CancelStellarOwnershipTransfer`, `TransferEvmOwnership`, `SetStellarDelegate`, `SetEvmDelegate`); routing/security (`SetStellarPeer`, `SetEvmPeer`, `SetStellarSendLibrary`, `SetStellarReceiveLibrary {library, grace_period}`, `RemoveStellarReceiveLibraryTimeout`, `SetEvmSendLibrary`, `SetEvmReceiveLibrary {library, grace_period}`, `RemoveEvmReceiveLibraryTimeout`, `SetStellarUlnConfig`, `SetEvmUlnConfig`, `SetStellarExecutorConfig`, `SetEvmExecutorConfig`, `SetStellarReceiveOptions`, `SetEvmReceiveOptions`); Stellar economics/liveness (`SetDefaultFee`, `SetDestinationFee`, `SetFeeRecipient`, `SetMessageInspector` (official `set_msg_inspector`), `SetInboundRateLimit {limit, window_seconds, mode}`, `SetOutboundRateLimit {limit, window_seconds, mode}`, `PauseEmergency`, `UnpauseEmergency`, `SetTtlConfig`, `FreezeTtlConfig`, `ExtendInstanceTtl`); Stellar RBAC (`GrantRole`, `RevokeRole`, `SetRoleAdmin`, `RemoveRoleAdmin`) restricted to the enumerated PAUSER_ROLE, UNPAUSER_ROLE, FEE_CONFIG_MANAGER_ROLE, RATE_LIMITER_MANAGER_ROLE exposed by the pinned OFT; packet lifecycle (`SendLeg`, `CommitVerification`, `ExecuteReceive`, `ContainOutbound`, `RestoreOutbound`, `RestoreFootprint`). EVM economic/rate-limit/RBAC variants do not exist unless exposed by the pinned standard OFT; those fields are inspect-only/fixed by ERC-20/OApp/Ownable surfaces. `IngestExecutedProposal` is a local custody effect, not a chain operation. It is derived by the CLI from a named command plus immutable desired state and live effective-state diff. No JSON target/calldata/XDR escape hatch exists. Serialization may carry a derived enum value for approval/proposal custody, but ingest re-derives it and requires byte-identical canonical form. Every variant maps one-to-one to `CommandEffect`, `MutationGate`, authority, state keys, and allowed transition. `OperationDraftV1` is a non-authoritative canonical route diff produced by `operation draft` from a parsed named command and command-specific typed argument struct; `CLOSED_ARGS.json` can populate only that closed struct, never target/calldata/XDR. A draft contains desired/observed state and proposed operation identity, but no sequence/nonce, executable envelope/calldata, simulation freshness, signer slots, or signable hash. It is allowed for known mainnet read-only analysis and can never be consumed by proposal/execution.
`ExecutablePlanV1` is testnet-only and never a user-created standalone input. Every granular direct domain command internally derives it under `MutationGate`, authority-domain/route locks, live sequence/nonce acquisition, exact transaction construction, and simulation. It binds operation, envelope/calldata, live pre-state, nonce/sequence, auth entries, simulation/config/code hashes, state/journal binding, and expiry. With `--execute`, that same in-memory plan is signed/broadcast. With `--proposal-out`, it is serialized inside `ProposalV1`. `proposal create --draft` is only a convenience for a non-authoritative `OperationDraftV1`: it re-derives a fresh executable plan from the named operation and current state; it never trusts draft transaction bytes. Mainnet rejects this conversion. There is no generic executable `--command/--args` escape hatch.
- Production mutation/proposal/ingest is explicitly out of scope for v1. Any live tuple classified as mainnet permits only read-only inspection, artifact verification, evidence import validation, reconciliation, and non-authoritative operation drafting; every command that could emit a signable proposal, access a signer, broadcast, or ingest an execution returns stable `production_mutation_unsupported_v1` before artifact/signature access. V1 contains no production approver keys, epochs, issuer, approval schema, Safe execution authority, emergency governance, or placeholder seam. A later separately reviewed authority specification is required before production mutation enters scope.
- `AssetPolicyV1`, embedded in `DesiredRouteV1`, includes asset class (`native_sac`, `issued_sep41`, or `test_only`), issuer/custodian authorization evidence digest, canonical wrapped-representation/destination acceptance evidence digest, custody controller set, separate custody-risk acceptance digest when Templar controls custody, and forbidden classic-issuer account. Production refuses missing claims and refuses any classic issuer account used as route operator, canary sender, destination recipient, delegate, or lockbox/custody address. Test-only routes must be explicitly environment-bound and cannot be approved for mainnet.
- `RouteStateV1`: mutable observed deployments and effective on-chain state, always bound to the desired-route digest. It also binds `OpeningCustodyV1`: finalized Stellar ledger sequence/hash/time and observed OFT lockbox, finalized EVM block number/hash and normalized supply, artifact/config hashes, and either independently proven zero prior packet activity or the digest of a complete imported historical `EvidenceBundleV1`. Adoption refuses an unauthenticated baseline; unknown history remains an explicit custody unknown and blocks zero-deficit claims.
- `AuthorityTopologyV1`, embedded in the desired route, maps deployment owner, LayerZero delegate, each explicit OFT operator/role holder, custody controller, rate-limit/containment admin, canary sender, and recovery executor to concrete on-chain authorizers. Each Stellar role is `{address, authority_kind}` where v1 `authority_kind` must be `classic_account`. For `classic_account`, the CLI fetches raw account ledger entries via `get_ledger_entries`, decodes `AccountEntry` through `stellar_baselib::xdr`, and reads signers, weights, and low/medium/high thresholds, binds the required threshold level per operation, and builds a standard multi-signature Stellar transaction envelope; the signed manifest cannot invent thresholds. Contract-account authorizers are out of scope for v1 and fail closed as `unsupported_stellar_authority_kind`; adding one requires a later reviewed schema/version and dedicated adapter fixtures. Each Stellar `OperationV1` has an explicit `StellarAuthorizationSpecV1` derived from the pinned official ABI: `{transaction_source, explicit_operator?, required_role_or_delegate, expected_auth_credentials}`. OFT admin/RBAC entrypoints encode the explicit `operator` argument and verify its exact official role (`PAUSER_ROLE`, `UNPAUSER_ROLE`, `FEE_CONFIG_MANAGER_ROLE`, `RATE_LIMITER_MANAGER_ROLE`, ); Endpoint/OApp library/config writes bind the current OApp delegate instead. Per-operation fixtures simulate the official invocation and qualify whether its auth entries are `SorobanCredentials::SourceAccount` for the same classic transaction source. Only qualified source-account operations support v1 envelope multisignatures. ### Step 2 — Versioned route state and ledger

Mutation locking uses one fixed two-phase protocol. Phase A performs a non-authoritative, read-only parse of the create-new route state solely to derive `{environment, vm, sender_or_safe}`, route canonical path, and their digests; it reserves no nonce and trusts no mutable decision. Acquire the authority-domain lock under the configured operation-store root first, then the route lock second. Under both locks, replay authoritative logs, re-read state/desired/environment/authority, and require the digests/key derived in Phase A to be unchanged; otherwise release and restart. Only then read/reserve the live sequence/nonce, simulate, construct, and durably record unsigned/signed hashes. Hold both locks through the `submission_pending` checkpoint. After that checkpoint the route lock may be released for long confirmation waits; the authority-domain reservation remains logically pending in its journal and a later process must reconcile the exact hash/nonce before another reservation. Different route files cannot bypass this sender-domain fence. Single-writer deployment is the default; multi-host writers require the operation-store root to be on storage providing the documented atomic create/lock/fsync semantics, otherwise startup returns `shared_operation_store_required`. Lock timeout is a typed busy result, never stale-lock deletion. Authority-domain then route is the only lock order and is concurrency-tested. State snapshots use same-directory temp + `sync_all` + rename + directory sync. Refuse symlink state/journal/lock paths. The journal is append-only JSONL with each record flushed and `sync_all`ed. Before broadcast, append `prepared` with canonical unsigned intent plus sender/sequence or sender/nonce; after signing, append `submission_pending` with signed transaction hash/envelope hash. Refuse symlink state/journal/lock paths.

EVM execution becomes terminal only after the configured confirmation depth and canonical block-hash recheck; a reorg returns the operation to pending and blocks dependent accounting/canaries. Stellar terminality binds successful transaction result/meta at the configured ledger-close policy.

`leg quote --out` is a non-authoritative create-new local artifact write and performs no nonce reservation or signable transaction construction. `leg send` requires a configured route, explicit raw amount, cap from state, destination codec validation, fresh quote, balance/supply snapshot, and configuration snapshot hash. It uses the crash-safe journal protocol: record intent and signed transaction hash before broadcast, then records source receipt/GUID/nonce and packet bytes as soon as observed.

`message watch` merges source receipt, LayerZero Scan, endpoint nonce/verification state, and destination logs without treating Scan as ledger authority. `message recover` uses an explicit capability matrix:
- EVM `ReceiveUln302.commitVerification`: permissionless after exact proof/header/payload checks.
- EVM `EndpointV2.lzReceive`: permissionless after committed verification and exact origin/receiver/message checks.
- Stellar ULN `commit_verification`: permissionless after exact packet/proof checks.
- Stellar OFT `lz_receive`: not generally permissionless; it requires authorization by the configured executor address. If the executor is a classic account, the CLI constructs the threshold-bound multisignature envelope. Contract-account executors return `unsupported_stellar_authority_kind`; insufficient authority returns `recovery_not_authorized`, both without mutation.
Each capability has a qualified contract code/hash/interface check. Unknown code or interface fails closed.
It refuses recovery if packet header/message bytes, payload hash, origin, receiver, library/config snapshot, and source event coordinates cannot be independently reconstructed and matched from durable ledger evidence. Recovery is executable without Scan or ordinary RPC history only when exact packet evidence was captured durably before pruning or an independently configured archival source supplies matching bytes. Otherwise it fails closed and reports `packet_evidence_unavailable`.

Reverse tests are separate commands; no automatic round trip. A stuck reverse remains an unresolved obligation and does not trigger another send unless `--allow-additional-obligation` is explicit and within cap.

Checks: deterministic state-machine tests for verified-not-committed, committed-not-executed, config-error packet, immutable old config snapshot, duplicate recovery, malformed Scan payload, and delayed DVN.

### Step 9 — Reconciliation
Normalize EVM supply to shared-decimal Stellar units. Classify obligations by direction and stage so locked collateral is counted once:
- Forward source accepted, destination not minted: unresolved forward.
- Forward minted: represented by EVM circulating supply, not unresolved forward.
- Reverse burned, Stellar not unlocked: unresolved reverse.
- Reverse unlocked: closed.

Use this executable stage table in `reconcile.rs` (all amounts normalized to Stellar raw common units after explicit fee/dust classification):

| Unique packet stage | observed lockbox delta from pre-route baseline | normalized EVM supply delta | `pending_forward_locked_not_minted` | `pending_reverse_after_burn` |
|---|---:|---:|---:|---:|
| forward source not confirmed | 0 | 0 | 0 | 0 |
| forward locked, destination not minted | +A | 0 | +A | 0 |
| forward minted/final | +A | +A | 0 | 0 |
| reverse source not confirmed | +A | +A | 0 | 0 |
| reverse burned, Stellar not unlocked | +A | 0 | 0 | +A |
| reverse unlocked/final | 0 | 0 | 0 | 0 |

Track three locations separately: OFT token lockbox balance, configured external `fee_deposit_address` token balance/deltas, and non-transferable decimal dust. The official `set_fee_deposit_address` recipient receives fees; external fee custody never enters `expected_lockbox`. `lockbox_retained_fee_or_dust` includes only exact units proven by events/balance deltas to remain at the OFT address (for example fee recipient equals OFT) plus non-transferable dust. Destination fees reconcile from exact debited, net locked, minted, burned, unlocked, and externally deposited amounts. Fee-address changes are append-only config events; missing historical fee-address evidence makes custody unknown. Duplicate GUID/nonces are one record plus a duplicate finding, never double-counted. Unknown/unindexed custody-affecting records make deficit `unknown` and exit nonzero rather than assuming zero. `expected_lockbox = supply + pending_reverse + lockbox_retained_fee_or_dust + pending_forward`; compare to the observed lockbox to produce surplus/deficit. Report raw lockbox, normalized supply, each stage bucket, lockbox-retained fee/dust, external fee-deposit custody/deltas, fee-address history, duplicates, unknown/unindexed messages, surplus, and deficit. Implement `health` in `reconcile.rs`/dispatch as the stable aggregate of reconciliation, nonce gaps, delivery-age thresholds, packet evidence TTL/archive risk, owner/delegate/role/config/receive-library-grace-timeout/artifact drift, and attempted mainnet mutation/proposal/ingest. `--fail-on-deficit` exits nonzero for deficit, unknown custody-affecting records, or inconsistent nonce gaps. Surplus is reported, not treated as success silently.

Checks: table-driven forward-unconfirmed, explicit `lockbox=A / supply=0 / pending_forward=A / deficit=0`, forward-locked, forward-minted, reverse-unconfirmed, reverse-burned, reverse-unlocked, fee recipient equal to OFT, external fee recipient, fee-address change, missing fee history, dust, duplicate GUID/nonce, and unknown packet cases. The proven `2,000,000 lockbox / 0 supply / 2,000,000 pending reverse / 0 deficit` fixture must pass exactly.

## 6. Acceptance criteria
1. CLI builds under the contracts workspace toolchain and passes workspace lints/tests; native Stellar mutation remains disabled unless the current-protocol/CreateContractV2/auth/meta/RestoreFootprint fixture gate passes.
2. RPC credentials are environment/file-backed and redacted; no secret value appears in argv display, logs, JSON output, state, snapshots, or test failure text.
3. Shared decimals are exactly 6 on both VMs and local token decimals >= 6; mismatches fail deployment/adoption. Pure codecs match official/proven golden vectors and reject malformed/overflow/dust inputs.
4. Artifact verification reproduces or validates exact official Stellar WASM and EVM wrapper bytecode from pinned inputs; drift blocks deployment.
5. `asset wrap` rejects USDC before mutation and creates deterministic, idempotent plans for eligible assets.
6. `route draft-config` only yields non-authoritative operation drafts; testnet executable nodes are planned one transaction at a time until both sides simulate successfully and required DVN/library/option support is proven; post-write effective state must match.
7. Dependency-aware per-write re-simulation is proven; a partial cross-chain configuration/deployment is persisted and safely resumable without duplicate deployment or hidden overwrite.
8. Authoritative journal/message hash chains detect interior tamper, torn tail, missing companions, fork, and snapshot divergence; coordinated whole-directory rollback is detected only with an independently supplied head anchor and otherwise reported as an explicit residual risk; state reconstructs from verified logs. Canary ledger records source tx, GUID, nonce, config snapshot, destination/recovery transactions, amounts, and monotonic status history.
9. Recovery capability tests prove EVM permissionless commit/receive, Stellar permissionless commit, authorized Stellar executor delivery, and fail-closed `recovery_not_authorized`; no recovery submits packet data that fails independent origin/receiver/payload-hash checks.
10. Adoption requires a finalized `OpeningCustodyV1` plus zero-history proof or complete imported history. Stage-delta reconciliation passes every forward/reverse stage, fee/dust, duplicate, and unknown-record table; unknown custody records exit nonzero, and the proven testnet fixture yields zero deficit with two unresolved reverse obligations.
11. Every mainnet-classified mutation, signable proposal creation, signature attachment, and execution ingest returns `production_mutation_unsupported_v1` before signer/artifact access; production read-only planning, inspection, evidence validation, artifact verification, and reconciliation remain available.
12. The exact deployment DAG resolves/binds the Stellar token/SAC first, derives and verifies the Stellar OFT address from an explicit salt, deploys/verifies Stellar then EVM artifacts, and makes every later testnet transaction independently adoptable. Deployment owner/delegate coupling and every planned split transition are separate transaction nodes with readback and block canaries on partial completion. Testnet classic-Stellar-multisig/Safe proposal artifacts verify live thresholds; all Stellar contract-account authorizers are rejected in v1.
13. TTL config/freeze/extend operations and health cover every official mutable/freezeable TTL surface; ownership begin uses relative `ttl: u32`, ttl-zero cancellation, and expiry readback. Directional containment preserves inbound receive on both VMs and is restorable to the exact previous configuration; global Stellar pause is rejected for routine containment.
14. `health` detects every defined custody/config/TTL/mainnet-mutation-attempt fixture with stable JSON and nonzero exit.
15. `EvidenceBundleV1` import proves exact public packet custody, rejects missing/inconsistent/secret-bearing evidence, and drives the recorded reverse-obligation fixture without assuming a nonexistent manifest. ## 7. Risks and mitigations
- Owner: CLI maintainer. Trigger: Soroban client protocol/API mismatch. Prevention: pin exact client/XDR versions and fixture signed envelopes. Detection: simulation fixture and protocol-version preflight. Recovery: native mutation remains disabled and implementation is blocked until the pinned client/protocol fixture gate passes; there is no Stellar submit fallback or silent switching in v1.
- Owner: release operator. Trigger: upstream artifact/ABI/XDR/version drift. Prevention: integrity lock and bytecode/WASM hashes. Detection: `artifact verify`, ABI selector/code-hash checks, and official-source golden vectors. Recovery: explicit lock update reviewed with source diff and regenerated golden artifacts.
- Owner: route operator. Trigger: one-sided partial mutation. Prevention: simulate all writes and ordered checkpoints. Detection: effective readback/state journal. Recovery: resume exact missing writes or contain outbound sends; never zero peers automatically.
- Owner: custody operator. Trigger: delayed/unindexed packet. Prevention: append source tx immediately and snapshot config. Detection: nonce/receipt/Scan reconciliation. Recovery: permissionless verified recovery or unresolved-obligation classification.
- Owner: security reviewer. Trigger: secret leakage through subprocess/errors. Prevention: native signing, zeroized secret wrappers, redacted executor, tests with sentinel secrets. Detection: output/log scans in tests. Recovery: stop, rotate disposable credential, invalidate affected deployment authority.
- Owner: product authority. Trigger: unsupported/canonical asset requested. Prevention: USDC hard refusal, typed asset authorization/custody claims, classic-issuer-account exclusion, and explicit asset topology. Detection: asset preflight. Recovery: use CCTP or obtain issuer/canonical-representation authorization outside this CLI.

## 8. Deliberate pre-mortem
1. Failure: CLI says configured after receipts, but effective DVN still points to a deprecated worker. Warning: requested/effective diff or `is_supported_message_lib=false`. Mitigation: effective readback is acceptance gate. Recovery: write supported DVN override, snapshot old packet obligations, rerun inspect.
2. Failure: forward mint succeeds, reverse burns, DVN never attests; operator sends more tests and grows locked obligations. Warning: reverse status remains nonterminal past timeout. Mitigation: one outstanding obligation cap and explicit override for another. Recovery: preserve obligation, use permissionless recovery if verifiable, otherwise stop new sends and escalate provider.
3. Failure: state crash or duplicate invocation loses GUID/nonce and understates custody. Warning: endpoint nonce exceeds journal. Mitigation: atomic state writes plus append source record immediately after receipt; nonce-gap check. Recovery: reconstruct from source logs/transactions, append `recovered_evidence`, and keep reconciliation unknown/nonzero until complete.

## 10. ADR
### Decision
Add `tools/oft-bridge-cli` as a thin native Rust operator CLI using native Soroban RPC/XDR and Alloy EVM RPC/signing. Keep injected, version-pinned official adapters only for contract builds, plus a narrowly qualified keystore-signing fallback. Persist versioned route state and an append-only message ledger.

### Drivers
Testability, credential safety, effective-state verification, reproducible official artifacts, and custody reconciliation.

### Alternatives considered
Fully native compilation/identity management; shell-first orchestration; chosen hybrid native runtime core.

### Why chosen
It avoids stdout/quoting fragility on money-moving paths without reimplementing upstream compilers or contract mechanisms. It reuses existing workspace dependencies and the sibling CLI's proven output/manifest/redaction conventions while keeping the new crate independent.

### Consequences
The CLI owns two typed RPC/signing adapters, qualified native LayerZero ABI/XDR codecs, and a serialized crash-safe operation journal. `soroban-client` and XDR protocol compatibility require explicit qualification because the repository contains both XDR 25 and XDR 26 consumers. Artifact builds still require pinned external tools. Live-provider delays remain operational facts and are represented as unresolved obligations, not hidden failures.

### Follow-ups
Frontend integration, production authority, mainnet mutation, and any separate Circle CCTP operator are separate plans. This deliverable is intentionally named and scoped as the non-USDC OFT operator; it does not claim to implement USDC routing.

## 11. Execution handoff
Sequential foundation first: crate/output/state/codec contracts. Then two independent lanes may run in parallel:
- Stellar adapter + artifact/build adapter.
- EVM adapter + ABI bindings/minimal wrapper artifact.
After their interfaces settle, one integration owner implements route configuration, then canary/recovery/reconciliation. A separate reviewer verifies secret boundaries and custody math. Main leader owns final targeted tests, read-only testnet inspection, diff-scoped Ponytail audit, and preservation of unrelated dirty files.

Recommended OMP agents: `task` for bounded implementation lanes, `security-reviewer` for signer/state/recovery boundaries, `reviewer` for final correctness. No worker/team runtime is required unless execution is explicitly started later.
